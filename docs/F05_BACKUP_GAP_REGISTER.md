# F-05 Backup & DR — Gap Register

Each gap is **documented, not repaired**, per the read-only restriction. Severity reflects impact if
the gap is never closed and the corresponding failure actually occurs.

| ID | Severity | Component | Gap | Evidence | Impact if unaddressed |
|---|---|---|---|---|---|
| BG-01 | **CRITICAL** | Orthanc index DB | **Never backed up at all.** Every existing dump targets `-d ris`; `orthanc` is a separate 22 MB database with zero coverage. | Verified by `psql -l` + grep of the newest dump's content | Total, permanent loss of the DICOM UID→file mapping on any Postgres failure — the 324 MB of DICOM files in `orthanc_storage` would become unreadable by Orthanc even though the files themselves still exist on disk |
| BG-02 | **CRITICAL** | DICOM storage volume | `orthanc_storage` (2489 instances, 10 studies, 324.2 MB) has **no backup of any kind**. | `docker system df -v` + live stats; `backups/` inventory | Any volume loss (disk failure, accidental `docker volume rm`, host failure) permanently destroys all clinical DICOM imagery with no recovery path |
| BG-03 | **CRITICAL** | PACS archive volume | `pacs_archive` (5 jobs, 3.97 MB, growing with use) has **no backup**; its DB metadata is only as current as the stale `ris` dump. | `docker system df -v`; backup-file-date comparison | Compressed archive files are the *only* copy in some workflows (archive's own docs note it is "copy-only" relative to Orthanc, but the compressed artifact itself still has no second copy) — loss here loses that compressed copy permanently |
| BG-04 | **HIGH** | All backups | **No automation.** Every existing backup was a one-off manual command run before a specific development milestone, not a schedule. | No cron/scheduler-task/script found anywhere in `scripts/`, `tools/`, or the backend's `@nestjs/schedule` jobs | Protection depends entirely on someone remembering to run a command; in practice, nothing has been backed up in the 2 days since the last manual snapshot despite five modules of new data being created |
| BG-05 | **HIGH** | All backups | **Staleness**: the newest backup of anything is 2026-11-14 17:06; it predates PACS Operations Modules 1–5 and the F-02 credential work entirely. | File timestamps vs. live data (5 archive jobs/9 transfer jobs exist live; 0 existed in the last dump) | A restore today would silently roll the system back ~2 days and lose real operational records, the break-glass admin account, and the credential rotations — a restore performed without this awareness could itself cause harm |
| BG-06 | **HIGH** | On-host storage only | Every backup artifact (`backups/`, the Docker volumes themselves) lives **on the same disk, same host** as the live system. | `backups/` is inside the project directory on `D:`; Docker volumes are under the same Docker Desktop/WSL2 VM | A single-disk or single-host failure (Scenario E) destroys the live data **and** every existing backup simultaneously — there is currently zero off-host protection |
| BG-07 | **MEDIUM** | Backup encryption | Backup dumps are plain gzip, **not encrypted**. | Inspected file format directly | A stolen/copied backup file exposes patient data (names, MRNs, clinical findings in `ris`) in the clear; this is a confidentiality gap, not an availability one |
| BG-08 | **MEDIUM** | Retention policy | **None exists.** All 5 RIS dumps are simply accumulating; no pruning, no daily/weekly/monthly tiering. | No retention script/config found | Left unaddressed long enough, this is a disk-space risk rather than a data-loss risk — lower urgency than BG-01–03 but will eventually matter |
| BG-09 | **MEDIUM** | Backup monitoring | **No alerting** exists for "a backup didn't run" or "a backup job failed" — because no backup job runs on a schedule in the first place (depends on BG-04 being closed first). | No monitoring hook found; Phase 8's alerting system exists but has no backup-related alert type wired in | A silent backup failure (once automation exists) could go unnoticed indefinitely, same failure mode as having no backup at all, just less visible |
| BG-10 | **MEDIUM** | Restore testing | Only **one** restore has ever been validated (the RIS logical dump, Phase 9, isolated container) — and that was 2 days ago, against data that's since changed materially. Orthanc's *file-volume* restore was explicitly **documented but never executed**, per the Phase 9 doc's own "safely-not-run" note. | `PHASE9_BACKUP_RESTORE.md` §"Orthanc — ... procedure documented, PG index portion VALIDATED" | Confidence in the one validated procedure is real but narrow (RIS DB only); the other three critical components (Orthanc index, Orthanc files, archive files) have **zero** validated restore evidence |
| BG-11 | **LOW** | Config/secrets backup | The project's own config files are backed up only as a single stale snapshot (2026-11-14); `.env`'s real secret values have **no backup anywhere**, by design (only a keys-only template exists). | `backups/config-20261114-151018/` inventory | Rebuilding after total loss requires the hospital's own separate secret-management process to supply real values again — this project cannot verify whether such a process exists outside this codebase |
| BG-12 | **LOW** | Full-host failure drill | Single-service restarts are well-tested (Phase 9, FR-1 through FR-7); **simultaneous multi-service failure and full host/node crash are explicitly marked NOT TESTED** in the existing documentation itself. | `PHASE9_FAILURE_RECOVERY.md` §"NOT TESTED" | Recovery-time and recovery-correctness for the realistic worst case (the whole machine dies) is currently an estimate, not a demonstrated result |

## Gaps NOT found (verified as sound, listed so they aren't mistaken for omissions)
- RIS logical backup **mechanism** itself (the `pg_dump`/gzip approach, and its one executed restore)
  is sound and was genuinely validated — the gap is frequency/automation/scope (BG-04, BG-05), not the
  method.
- Redis requires no dedicated backup strategy — its contents are either re-issuable or self-healing by
  design, confirmed by code inspection and the Phase 9 restart test.
- The application-level archive SHA-256 integrity check is real and already working correctly — it
  protects against *silent corruption of the compressed artifact*, which is a different problem from
  *the artifact having no second copy at all* (BG-03). Both matter; neither substitutes for the other.
